# The Duplicate-Quad Fixture Can No Longer Be Built

## Status: OPEN — a correctness guard has silently lost its fixture

`sp_lead_dup` exists for one reason: to hold entities carrying DUPLICATE anchor
quads, so that a rewrite dropping the `DISTINCT` above a semi-join is caught.
`lead_fixtures.py` says why it was built:

> Every other fixture here is generated by `generate_lead_dataset.py`, which
> emits each triple once — so each entity has exactly one `vitaltype KGEntity`
> row and one `hasKGEntityType` row, and a rewrite that drops the DISTINCT is
> sound on that data no matter how wrong it is in general. That is why the
> semi-join shipped returning 34,659 rows for 34,423 entities on production data
> with every bench green.

`scripts/load_duplicate_quad_dataset.sh` now fails:

    psycopg.errors.UniqueViolation: duplicate key value violates unique
    constraint "sp_lead_dup_rdf_quad_pkey"
    CONTEXT: COPY sp_lead_dup_rdf_quad, line 94

`rdf_quad` gained a PRIMARY KEY on `(subject_uuid, predicate_uuid, object_uuid,
context_uuid)` — `scripts/migrate_quad_pk_dedup.py` — and the fixture's entire
content is rows that key forbids.

## Why this matters

Two benches (`query.kgquery.duplicate_anchor_quads[generic]` and `[specific]`)
skip for want of the space, and skipping reads as green. The property they guard
is the one that shipped a wrong answer once already, on production data, with
every other bench passing.

## The same root cause bit twice today

`test_migrate_nonpartitioned_space_preserves_data` inserted duplicate quads to
prove the partition migration dedups them, and failed for exactly this reason.
It was fixed by DROPPING THE PRIMARY KEY in the fixture, because a pre-PK space
is precisely what that migration exists to convert.

The same move is available here and needs a decision rather than a copy: a
duplicate-quad fixture is representable only as a pre-PK space, so either the
loader drops the constraint the way that test does, or the property moves to a
test that builds its own table.

## What to check first

Whether `sp_lead_dup` on the HOST cluster predates the PK and still holds its
duplicates — if so, the fixture exists but only where nothing reads it, which is
`issues/055`'s shape and would explain why this went unnoticed.
