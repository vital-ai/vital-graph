# DISTINCT Elision Returns Duplicate Rows When the Anchor Has Duplicate Quads

## Status: FIXED 2026-08-07 — verified against ground truth on both paths

`distinct_redundant` is gone: `semijoin.py` no longer marks it and
`emit_distinct` no longer honours it. The blocking-node problem that motivated
the elision is handled where it belongs — `emit_slice._emit_two_phase` emits
`SELECT DISTINCT ON (key)` on exactly the ORDER BY key.

**It has to be `DISTINCT ON`, not `DISTINCT`.** Plain `DISTINCT` lets the planner
dedup with a `HashAggregate` and sort afterwards, which is blocking: measured
81–122 s, probing all 35,987 candidates. `DISTINCT ON` has a single
implementation, Unique over sorted input, so the index-ordered scan survives and
LIMIT stops at 52 probes.

| | before | after |
|---|---|---|
| rows / distinct (rewrite fires) | 34,659 / 34,423 | **34,423 / 34,423** |
| duplicate rows | 236 across 82 entities | **0** |
| page of 50, generic anchor | 2–4 ms | 3 ms |
| page of 50, specific type | n/a (rewrite skipped) | 2 ms |

Deduplicated set md5 `dd0b028c…` on both paths, matching the set-based control
and the recorded ground truth of 34,423.

`semijoin.py` marks `hints['distinct_redundant']` on the DISTINCT above a
rewritten join, so `emit_distinct` drops it. The stated reason:

> EXISTS yields at most one row per outer row, so the DISTINCT no longer removes
> anything

The first clause is true and the second does not follow. EXISTS does not
*multiply* the outer rows, but it also does not *deduplicate* them — and the
outer side was never guaranteed to be one row per entity. Where the anchor
pattern matches a subject more than once, the DISTINCT was removing something,
and dropping it puts duplicates in the result.

## Measured — same criteria, same space, one path duplicates

22.4M-quad restored production space. Full result set, not a page.

| path | rows | distinct entities | duplicate rows |
|---|---|---|---|
| semi-join (rewrite fires) | **34,659** | 34,423 | **236 across 82 entities** |
| set-based (rewrite skipped) | 34,423 | 34,423 | 0 |

The **deduplicated** sets are byte-identical (md5 `dd0b028c…` both ways) and match
the ground truth of 34,423 recorded in
`planning/planning_performance/high_cardinality_slot_value_query_plan.md`. So the
rewrite selects exactly the right entities. It just returns 82 of them more than
once.

## Root cause — confirmed against the data, not inferred

The anchor BGP is `?entity vitaltype KGEntity` within the graph. Counting
subjects with more than one such quad:

```
subjects_with_duplicate_anchor_rows | extra_rows
                                 82 |        236
```

Exactly the observed duplication. `rdf_quad` can hold the same
`(subject, predicate, object, context)` more than once — the rows differ by
`quad_uuid` / `dataset` — so the anchor legitimately emits several rows per
entity. The pre-existing `SELECT DISTINCT` collapsed them and nobody had to
think about it. Removing it exposes the multiplicity directly to the caller.

## Why the benches did not catch it

Two independent reasons, and both are worth fixing:

1. **The verification was a subset check.** `issues/040` records that every page
   was verified as a subset of the true match set. A duplicated page is still a
   subset — the check cannot see multiplicity. Set membership and row
   multiplicity are different properties and only the first was asserted.
2. **The lead fixtures have no duplicate quads.** They are generated by
   `scripts/generate_lead_dataset.py`, which emits each triple once, so the
   anchor is one row per entity there by construction and the elision is sound
   on exactly the data it was measured against.

## Impact

Every query where the rewrite fires *and* the anchor has duplicate quads:

- a page of 25 can show the same entity twice, so the caller sees fewer than 25
  distinct results without any indication why;
- `include_total_count` over-counts — it counts rows, and the rows are inflated;
- offset paging drifts, since the offsets index a longer sequence than the
  distinct set.

Note this is the path that *works* — the fast one. `issues/045` is about the
rewrite failing to engage; this is about what it does when it does engage.

## Fix

The elision needs a precondition the pass does not currently check: **the outer
side must already be duplicate-free with respect to the projected variables.**
That is not knowable from the plan shape alone, because it depends on whether
the data contains repeated quads.

Options:

1. **Do not elide; make the DISTINCT cheap instead.** The stated motive for
   eliding was that `Unique`/`HashAggregate` is a blocking node that stops LIMIT
   terminating early. In the two-phase path the first phase already pages flat
   uuids, so a `DISTINCT` there may no longer block — worth measuring before
   assuming the elision is needed at all.
2. **Deduplicate the anchor instead of the result** — emit the outer side as
   `SELECT DISTINCT subject_uuid` so it is one row per entity by construction,
   which restores the premise the elision rests on and keeps the non-blocking
   shape.
3. **Elide only when the anchor is provably unique**, e.g. keyed on a primary
   key rather than a quad pattern. Narrow, and hard to establish for quad data.

(2) looks closest to the intent. Whichever lands, the assertion below must come
with it.

## Added to the suite — with a fixture that can actually regress it

`test_duplicate_anchor_quads_do_not_reach_the_result`, parametrised over generic
and specific entity type, against a new fixture built for this:

| | |
|---|---|
| generator | `scripts/generate_duplicate_quad_dataset.py` |
| end-to-end build | `scripts/load_duplicate_quad_dataset.sh` |
| fixture | `lead_fixtures.DUP` — `sp_lead_dup`, 500 entities |
| duplication | 100 entities carry both anchor quads 2-4x — 398 extra rows |

Anchors only (`vitaltype KGEntity` and `hasKGEntityType`), because those are what
the semi-join's outer side scans. Frame and slot triples are left alone: EXISTS
is insensitive to multiplicity on the probe side by construction, so duplicating
there would test nothing and would skew the manifest's match counts.

**Verified by reintroducing the bug.** With `DISTINCT ON` reverted to a plain
projection, the two DUP tests fail (`10 duplicate entit(y/ies) in a 25-row
page`) — and the four tests over the *generated* fixtures still pass. That is
the whole argument for a separate dataset: on data where every triple appears
once, the assertion is true no matter what the code does.

The test also asserts the fixture is non-degenerate (`duplicate_anchor_rows > 0`)
before trusting a pass, so a regenerated-without-duplicates fixture fails loudly
instead of going quietly green.

## Reproduce

```bash
PROBE_VERIFY=1 PROBE_PAGE_SIZE=200000 \
  PROBE_ENTITY_TYPE="http://vital.ai/ontology/haley-ai-kg#KGEntity" \
  ./scripts/probe_semijoin_entity_query.sh     # 34,659 rows / 34,423 distinct

PROBE_VERIFY=1 PROBE_PAGE_SIZE=200000 \
  ./scripts/probe_semijoin_entity_query.sh     # 34,423 rows / 34,423 distinct
```

The script prints row count, distinct count, duplicated keys, and an md5 of both
the row list and the deduplicated set.
